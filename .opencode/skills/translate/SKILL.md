# Translation Reference

This skill provides format rules, terminology, and guidelines for translating fcitx5-js. The `/translate` command orchestrates the workflow.

## Project Overview

fcitx5-js has **one i18n system**: C++ gettext. Source strings come from `_()` / `N_()` calls in C++ headers (primarily `webpanel/webpanel.h`) plus the Desktop file `wasmnotifications/notifications.conf.in.in`, with `po/base.pot` as the template and `po/<locale>.po` for each language. `po/base.pot` is generated by the `pot` CMake target (`po/CMakeLists.txt`).

Most webpanel strings are **identical** to the sibling fcitx5-macos project (`../fcitx5-macos/`). Reuse the existing translation from `../fcitx5-macos/po/<lang>.po` whenever the `msgid` matches; only translate the few strings that differ.

## C++ Localization (gettext .po)

### File Format

Standard GNU gettext format. Each entry:

```po
#: webpanel/webpanel.h:line_number
msgid "English text"
msgstr "Translated text"
```

### Files

| File | Path |
|------|------|
| POT template | `po/base.pot` |
| Language list | `po/LINGUAS` |

### Sync

Regenerate `po/base.pot` from all sources (C++ header + Desktop file) and merge into every language file:

```sh
xgettext --c++ --keyword=_ --keyword=N_ webpanel/webpanel.h -o po/base.pot
xgettext --language=Desktop wasmnotifications/notifications.conf.in.in -j -o po/base.pot
cd po && for lang in $(cat LINGUAS); do msgmerge -U $lang.po base.pot; done
```

The second `xgettext` call uses `-j` to append the Desktop file's `Name` string (e.g. `Notifications`) into `base.pot`. This must match `po/CMakeLists.txt`, which is the source of truth for what generates `base.pot`.

### Editing Rules

- **Encoding**: UTF-8.
- **Header**: Update `PO-Revision-Date` and `Last-Translator` when modifying a file.
- **Content-Transfer-Encoding**: Must be `8bit` (the standard gettext value for UTF-8 content).
- **Format**: Follow standard `.po` file conventions exactly.
- **Placeholder tokens**: `%d`, `%s`, `%1$d`, `%1$s` etc. MUST be preserved exactly.
- **`fuzzy` flag**: Only use when you are unsure of the translation. Mark it and leave a comment explaining the uncertainty. Fuzzy entries are NOT shown to users.
- **Empty `msgstr ""`**: Means untranslated. Every `msgid` must have a non-empty `msgstr` in completed translations.
- **Fuzzy/continuation lines pitfall**: A fuzzy or untranslated entry may look like:
  ```po
  #, fuzzy
  msgstr ""
  "Old fuzzy translation text here"
  ```
  Continuation lines (quoted strings after `msgstr ""`) are valid PO syntax — they exist so long translations can be split across multiple lines. When filling in the translation, replace the **entire block** (the `#, fuzzy` flag if present, the `msgstr ""` line, and all continuation lines) with a single `msgstr "New translation"`. If you only replace the `msgstr ""` line, the orphaned continuation lines are silently concatenated, appending stale text to your translation. Always validate after editing (see Validation below).

### Reusing fcitx5-macos Translations

For any `msgid` that also exists in `../fcitx5-macos/po/<lang>.po`, copy that file's `msgstr` verbatim. These webpanel strings are identical across the two projects, so the existing translations already apply. Only the following strings differ and must be translated from scratch:

- Strings present in fcitx5-js but not fcitx5-macos (e.g. `Radius of blur (px)`).
- Strings whose fcitx5-macos translation maps a caret-specific term differently (check `Caret`/`Cursor`, `Follow caret`/`Follow cursor` in the target language).

After copying or translating, run `msgcmp` (see Validation) to confirm no `msgid` is missing.

### PO File Header Template

Use this as the header when creating a new `.po` file, adapting the fields:

```po
msgid ""
msgstr ""
"Project-Id-Version: fcitx 5\n"
"Report-Msgid-Bugs-To: \n"
"POT-Creation-Date: YYYY-MM-DD HH:MM±ZZZZ\n"
"PO-Revision-Date: YYYY-MM-DD HH:MM±ZZZZ\n"
"Last-Translator: Your Name <email>\n"
"Language-Team: Language Name\n"
"Language: <lang>\n"
"MIME-Version: 1.0\n"
"Content-Type: text/plain; charset=UTF-8\n"
"Content-Transfer-Encoding: 8bit\n"
```

### Creating a New Language

When adding a language that doesn't exist yet (e.g. `vi`):

1. **Run sync first** to ensure `po/base.pot` is up to date:
   ```sh
   xgettext --c++ --keyword=_ --keyword=N_ webpanel/webpanel.h -o po/base.pot
   xgettext --language=Desktop wasmnotifications/notifications.conf.in.in -j -o po/base.pot
   ```
   (The second command appends the Desktop file strings — `-j` merges into the existing `base.pot`; this mirrors `po/CMakeLists.txt`.)

2. **Create `po/<lang>.po`** from `po/base.pot`:
   - Copy the header block from an existing `.po` file (e.g. `zh_CN.po`) and adapt it.
   - Set `Language: <lang>`, update `Last-Translator` and `PO-Revision-Date`.
   - Set `Content-Transfer-Encoding: 8bit` (NOT `eight` — this is the standard gettext value).
   - Reuse matching `msgstr` from `../fcitx5-macos/po/<lang>.po` where the `msgid` matches.
   - Translate every remaining `msgstr`.

3. **Update `po/LINGUAS`** — add the POSIX locale code (e.g. `vi`), one per line, in alphabetical order.

### Validation

```sh
msgfmt -c po/<lang>.po -o /dev/null
msgcmp po/<lang>.po po/base.pot
```

- `msgfmt -c` — checks PO syntax and compilation (format errors, placeholder mismatches, duplicate msgids).
- `msgcmp` — checks translation completeness against the template (missing or extra msgids).

## General Translation Rules

1. **Keep translations concise** — UI space is limited. Prefer short, natural phrasing.
2. **Maintain consistency** — If a term is translated one way, use the same translation everywhere.
3. **Respect platform conventions** — Use terminology that the target platform's users would expect.
4. **No machine-translation artifacts** — Avoid overly formal or stilted phrasing. Translations should read naturally.
5. **Do not translate** — brand names, file paths, command names, technical identifiers, or code. Also keep well-known UI/design terms in their original form if translating them would cause confusion.
6. **Preserve format specifiers** — all `%d`, `%s`, `%1$d`, positional specifiers etc. must appear in the translation in the same order.
7. **Punctuation** — Use the punctuation conventions of the target language (e.g. Chinese full-width ？。、 vs English half-width ?.).
8. **Reuse sibling translations** — For msgids that match `../fcitx5-macos/po/<lang>.po`, copy the existing `msgstr` rather than retranslating.

## Output Format

When translating, present changes clearly:

- Show the `msgid`/`msgstr` blocks that were added or modified.
- Group changes by file.
- If adding new entries, mention the source file and line number.
